# MeshHiPS OBJ Normal And Light Analysis

## Scope

This report analyses the current `astro-viewer` handling of:

- satellite OBJ normals
- MeshHiPS OBJ tile normals, using the Moon dataset as the observed case
- lighting in `MeshHiPSShaderProgram`

No source code changes are proposed as implemented changes in this report.

## Summary

The satellite OBJ and MeshHiPS Moon tiles follow different normal paths.

`SatelliteObjectGL` loads a small controlled OBJ asset with explicit `vn` normals and calls:

```ts
OBJMeshParser.parse(text, {
  preferFileNormals: true,
  generatedNormals: "flat",
});
```

It also creates the shader with:

```ts
new MeshHiPSShaderProgram(gl, {
  twoSidedLighting: true,
  markerLighting: true,
});
```

`MeshHiPSTile` loads each terrain tile with:

```ts
OBJMeshParser.parse(text)
```

That means:

- `preferFileNormals` defaults to `true`
- `generatedNormals` defaults to `"smooth"`
- if the tile OBJ has no usable `vn`, normals are generated by averaging face normals
- lighting is one-sided by default

The Moon MeshHiPS tiles currently contain only `v` and `f` records, no `vn` records. Their face winding generates inward-facing normals for the sampled tiles inspected. This is likely the main cause of unstable or visually incorrect lighting.

## Relevant Code Paths

### Satellite OBJ

File:

```text
src/model/terra/SatelliteObjectGL.ts
```

The satellite path:

1. fetches a single OBJ
2. parses with explicit normal preferences
3. prefers file normals
4. uses flat fallback if file normals are missing
5. uses two-sided marker lighting
6. applies a per-frame model matrix for position/orientation

The demo asset:

```text
src/html/test-data/satellite/simple_satellite.obj
```

includes explicit `vn` records and face tokens such as:

```obj
f 1//1 4//1 3//1 2//1
```

The parser therefore duplicates vertices by `positionIndex/normalIndex` pair when needed and keeps hard-edged faces stable.

### MeshHiPS Moon Tiles

Files:

```text
src/model/meships/MeshHiPSTile.ts
src/model/meships/OBJMeshParser.ts
```

The tile path:

1. fetches many OBJ tile files
2. parses each tile with default parser options
3. uses file normals only if all triangulated face vertices reference valid normals
4. otherwise generates smooth averaged normals
5. renders with one-sided lighting

The Moon dataset path inspected:

```text
../astrobrowser-infra/docker/meships-local/mhips-moon/
```

The tile OBJ files inspected contain:

```text
v  ... vertex records
f  ... quad face records
```

but no:

```text
vn ... normal records
```

## Observed Tile Normal Data

Sampled Moon tiles:

```text
Norder0/Dir0/Npix0.obj
Norder1/Dir0/Npix0.obj
Norder2/Dir0/Npix100.obj
Norder3/Dir0/Npix500.obj
```

Each sampled tile has:

```text
4225 vertices
4096 quad faces
0 file normals
```

After fan triangulation, each has:

```text
8192 triangles
```

For each sampled tile, the raw face normal was compared with the radial direction from the sphere centre to the triangle centroid.

Result:

| Tile | Outward triangles | Inward triangles | Average dot(normal, radial) |
| --- | ---: | ---: | ---: |
| `Norder0/Dir0/Npix0.obj` | 0 | 8192 | -0.9980 |
| `Norder1/Dir0/Npix0.obj` | 0 | 8192 | -0.9986 |
| `Norder2/Dir0/Npix100.obj` | 0 | 8192 | -0.9808 |
| `Norder3/Dir0/Npix500.obj` | 0 | 8192 | -0.9717 |

This indicates consistent inward winding for these Moon tiles.

The generator code in `3dhips/src/hips_obj_from_mesh.ts` writes each cell as:

```ts
const a = j * vertsPerSide + i;
const b = a + 1;
const c = (j + 1) * vertsPerSide + i + 1;
const d = c - 1;
fs.writeSync(fd, `f ${a + 1} ${b + 1} ${c + 1} ${d + 1}\n`);
```

With the current coordinate convention, that order appears to produce inward normals for the Moon output.

## Normal Handling Difference

### Satellite

Satellite OBJ:

- has explicit `vn`
- uses `preferFileNormals: true`
- uses `generatedNormals: "flat"` only as fallback
- duplicates vertices for hard-edged normal splits
- uses two-sided lighting

This is appropriate for a low-poly hard-edged model.

### Moon MeshHiPS

Moon tile OBJ:

- has no explicit `vn`
- uses default smooth generated normals
- derives normals from face winding
- current winding appears inward
- renders with one-sided lighting

This is risky for spherical terrain tiles. Smooth normals are acceptable for terrain only if the input winding is correct or if normals are corrected to the expected outward surface direction.

## Likely Causes Of Flicker / Unstable Triangles

### 1. Inward Generated Normals

Because the tile OBJ has no `vn`, `OBJMeshParser` computes normals from face winding. For sampled Moon tiles, those normals point inward.

With one-sided diffuse lighting:

```glsl
max(dot(normal, lightDir), 0.0)
```

an inward normal can produce lighting that feels inverted, view-dependent, or unstable when the mesh rotates relative to a fixed world-space light.

The triangles are probably not geometrically flipping. The apparent flicker is likely lighting contrast changing abruptly across tile boundaries, newly loaded tiles, or triangles whose generated normals do not match the expected outward surface.

### 2. Tile-Local Smooth Normals

Smooth normals are computed per OBJ tile in isolation. Vertices on tile borders are duplicated across tile files, so normals at shared borders are averaged only from faces inside each tile.

That can produce visible seams or slight lighting discontinuities between adjacent tiles, especially at high zoom.

### 3. Mixed Order Rendering During Zoom

`MeshHiPS.draw(...)` renders coverage tiles grouped by order:

```ts
const orders = Array.from(byOrder.keys()).sort((a, b) => a - b)
```

During zoom, parent and child tiles can coexist while new tiles are loading. If overlapping parent/child geometry is drawn at nearly the same surface depth, depth fighting can look like triangle flicker.

This is separate from normals, but the visual symptom can be similar. The Moon properties also report:

```json
"recommendedMaxOrder": 1,
"maxOrder": 3,
"oversampled": true
```

Oversampled high-order terrain plus parent/child overlap increases the chance of visible instability during zoom transitions.

### 4. Fixed World-Space Light

`MeshHiPSShaderProgram` currently uses a fixed light direction:

```glsl
vec3 lightDir = normalize(vec3(0.45, 0.8, 0.35));
```

This is a world/model-space style light, not camera-relative. When the user rotates the sphere, the light stays fixed from one side of the world. That can be physically valid for a Sun-like light, but it is not ideal for a navigation/debug viewer where the user expects stable shape readability.

The rim term is also fixed:

```glsl
dot(normal, vec3(0.0, 0.0, 1.0))
```

It does not use the actual camera/view direction.

## Lighting Analysis

The shader receives:

```glsl
uniform mat4 uPMatrix;
uniform mat4 uVMatrix;
uniform mat4 uMMatrix;
```

The vertex shader transforms normals with the model matrix:

```glsl
vNormal = normalize((uMMatrix * vec4(aVertexNormal, 0.0)).xyz);
```

The fragment shader then compares that world-space normal to a constant vector:

```glsl
vec3 lightDir = normalize(vec3(0.45, 0.8, 0.35));
```

The view matrix is not used for lighting. Therefore the light is not attached to the camera.

For an interactive viewer, a better default would be a camera-relative light:

- light roughly behind the camera
- slightly oblique, not exactly equal to the view direction
- stable in screen space while the user rotates the globe

Conceptually:

```text
lightDirWorld =
  normalize(cameraForwardWorld * -1
          + cameraRightWorld * 0.25
          + cameraUpWorld * 0.35)
```

or equivalently pass a `uLightDirectionWorld` uniform from the camera each draw.

This would keep terrain readable during rotation. A later physically motivated Moon/Sun mode could still use a real Sun vector.

## Recommended Fix Options

### Option A: Fix MeshHiPS Tile Generation

Best data-level fix.

Update the 3D HiPS tile generator so it writes either:

1. outward face winding, or
2. explicit outward `vn` normals referenced by faces.

For spherical terrain, robust normals can be:

- radial normals: `normalize(position)`
- DEM/terrain gradient normals, if local surface relief matters
- face normals corrected outward by checking `dot(faceNormal, centroid)`

Pros:

- fixes all consumers of the dataset
- keeps viewer parser simple
- avoids per-load correction work

Cons:

- requires regenerating and republishing the Moon dataset
- requires validating all existing MeshHiPS outputs

### Option B: Add Viewer-Side MeshHiPS Normal Correction

Best short-term viewer-side fix.

For MeshHiPS terrain tiles only, after parsing:

1. detect whether generated normals are mostly inward
2. flip normals if `average dot(normal, position) < 0`
3. optionally use radial normals for spherical tiles

This should not be applied blindly to arbitrary OBJ models. It belongs behind MeshHiPS-specific config or descriptor metadata.

Possible descriptor property:

```text
mesh_normal_mode=radial
```

or config:

```ts
normalMode?: "obj" | "generated-smooth" | "radial" | "auto-outward"
```

Pros:

- no need to regenerate the dataset immediately
- can fix old datasets
- keeps satellite OBJ behavior unchanged

Cons:

- adds viewer-side interpretation of MeshHiPS geometry
- radial normals may underrepresent actual terrain relief
- automatic flipping must be carefully scoped

### Option C: Use Two-Sided Lighting For MeshHiPS

Quick visual mitigation, not a real normal fix.

Create `MeshHiPSShaderProgram` for terrain with:

```ts
twoSidedLighting: true
```

This would make inward normals less catastrophic because lighting uses:

```glsl
abs(dot(normal, lightDir))
```

Pros:

- minimal change
- reduces dark/backfacing artifacts

Cons:

- hides normal errors rather than fixing them
- loses meaningful light direction on terrain
- can make relief look flatter or ambiguous

### Option D: Camera-Relative Light

Recommended alongside normal correction.

Add a uniform light direction and update it from the camera each draw. Default to an oblique camera-relative light for viewer/debug mode.

Pros:

- improves readability while rotating/zooming
- reduces perception of side-fixed lighting
- useful for both MeshHiPS and satellite OBJ

Cons:

- requires shader API change
- not physically Sun-correct
- should be a mode/config, not the only possible lighting model

## Recommended Plan

1. Add a MeshHiPS-specific normal mode in `astro-viewer`.
2. For terrain tiles, detect inward normals and flip them or use radial normals.
3. Keep `SatelliteObjectGL` behavior unchanged.
4. Add tests around `OBJMeshParser` or a MeshHiPS normal utility:
   - OBJ without `vn`
   - inward spherical tile winding
   - outward correction
   - satellite-style file normals remain untouched
5. Add camera-relative oblique light as a shader option.
6. Later, patch `3dhips` generator to emit outward winding and/or explicit `vn`, then regenerate Moon MeshHiPS.

## Short-Term Recommendation

For the immediate Moon flicker/lighting issue, do not change the generic parser default.

Instead:

- keep generic OBJ parser semantics stable
- add MeshHiPS tile-level normal correction
- use radial or auto-outward normals for spherical MeshHiPS datasets
- add a camera-relative light option for MeshHiPS rendering

This avoids regressing `SatelliteObjectGL` and other OBJ consumers.

## Long-Term Recommendation

Patch `3dhips` so generated spherical MeshHiPS OBJ tiles contain correct outward normals.

The viewer should still keep defensive normal correction because old datasets may remain published, but the canonical Moon dataset should be regenerated with valid normals.

## Open Questions

- Should MeshHiPS normals represent pure sphere radial direction or local terrain relief?
- Should `mesh_normal_mode` be encoded in MeshHiPS `properties`?
- Should camera-relative light be the default only for dev/test UI, or for all MeshHiPS rendering?
- Should parent/child tile overlap during loading be adjusted to reduce depth fighting separately from normal fixes?
- Should MeshHiPS render with polygon offset or child-first replacement to reduce zoom-transition flicker?


Personal recomendation: go for long-term recommendation and patch the 3dhips!
